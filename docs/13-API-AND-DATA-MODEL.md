# 13. API and Data Model

Draft contracts for Phase 3. Names and fields will evolve; keep this file in sync with the OpenAPI schema generated by the backend.

## Conventions

- JSON over HTTPS; versioned prefix `/v1`.
- Authentication via secure session cookie; state-changing requests require CSRF protection ([11](11-SECURITY.md)).
- Every resource ID is random (UUID/ULID). Every query is scoped to the authenticated user.
- Unknown fields are rejected. All requests and responses use typed schemas.
- Long operations return a **job** to poll (or stream) rather than blocking.
- Errors use a common shape: `{ "error": { "code": "...", "message": "...", "request_id": "..." } }` with no stack traces and no content echoing.
- Every analysis response includes `engine_version`, `scorer_version`, `model_version` and `prompt_version`.

## Core data model (draft)

```
User
  id, email (verified), name, college_year, target_roles[], created_at, deleted_at
Consent
  id, user_id, type, granted, version, timestamp
Resume
  id, user_id, label, source_file_ref (nullable after deletion), content_hash,
  status, retention_until, created_at
ResumeVersion
  id, resume_id, structure (JSON), engine_version, created_at
Claim
  id, resume_version_id, text_span, kind (skill|bullet|project|education),
  level (0..3), risk (bool), reasons[], classifier_version
LedgerFact
  id, resume_id, claim_id (nullable), key, value, unit, source (user_stated|repo_derived|placeholder),
  evidence_ref (answer id / repo path), created_at, edited_at
EvidenceSession
  id, resume_id, status, question_log[] (stored minimally), created_at
Project
  id, user_id, repo_ref, signals (JSON), originality (JSON), upgrade_paths[], analyzed_at
JobDescription
  id, user_id, text_hash, text (encrypted), requirements (JSON), created_at
Triage
  id, jd_id, resume_version_id, verdict (apply|stretch|skip), reasons[], gap_plan[], scorer_version
TailoredVersion
  id, jd_id, resume_version_id, content (JSON), diff (JSON), model_version, prompt_version, status
Export
  id, tailored_id, format, created_at, expires_at
AuditEvent
  id, user_id, action, ip_hash, user_agent_hash, timestamp
```

All user-owned tables carry `user_id` (directly or via parent) and are queried with it. Resume text, JD text and tokens are encrypted at the field level where practical.

## Fact Ledger schema

The ledger is the contract between humans, the model and the validator.

```json
{
  "resume_id": "01J...",
  "facts": [
    {
      "id": "f_001",
      "claim_id": "c_014",
      "key": "users_count",
      "value": 120,
      "unit": "users",
      "source": "user_stated",
      "evidence": "answer_7"
    },
    {
      "id": "f_002",
      "claim_id": "c_014",
      "key": "tech",
      "value": "Redis",
      "source": "repo_derived",
      "evidence": "repo:app/cache.py"
    },
    {
      "id": "f_003",
      "claim_id": "c_014",
      "key": "latency_improvement_pct",
      "value": null,
      "source": "placeholder",
      "evidence": null
    }
  ]
}
```

### Validator contract

Input: generated text + facts for the claim. Output:

```json
{
  "ok": false,
  "violations": [
    { "type": "number_not_in_ledger", "text": "40%", "span": [57, 60] }
  ],
  "placeholders_needed": ["latency_improvement_pct"]
}
```

Rules: any number, unit, tool/technology, organisation or date in the output must match a ledger fact (or be present in the original resume text for that claim). Violations either trigger regeneration or are converted to placeholders. Export requires `ok: true` and zero placeholders.

## Model task interface (internal)

Request:

```json
{
  "task": "draft_bullet",
  "claim_id": "c_014",
  "ledger_facts": [ ... ],
  "resume_excerpt": "...",
  "style": { "voice_sample_ref": "...", "max_words": 28 },
  "prompt_version": "bullet-v3"
}
```

Response (schema-constrained):

```json
{
  "bullet": "...",
  "facts_used": ["f_001", "f_002"],
  "needs_input": ["latency_improvement_pct"]
}
```

Other tasks: `ask_questions`, `grade_answer`, `generate_interview_questions`, `explain_triage`. Each has a versioned schema.

## Versioning and compatibility

- Semantic versions for `engine`, `scorer`, `prompt` and `model`; stored with every result.
- Scores are reproducible by pinning versions; changing a version triggers the evaluation gate ([07](07-EVALUATION-AND-QUALITY.md)).
- Database migrations are reviewed and reversible; never drop user data without a deletion request path.

## Rate limits and quotas (starting points)

| Scope | Limit |
|---|---|
| Auth endpoints | Strict per IP and per email, with backoff |
| Uploads | Few per hour per user; capped total size |
| Model-backed endpoints | Per-user concurrency and daily token quotas |
| GitHub analysis | Few repos per day per user |
| Public waitlist | Per IP and per email, with bot protection |

Tune with real usage; return `429` with `Retry-After`.
